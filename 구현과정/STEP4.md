# STEP 4 — OCR 처리

> 상태: **보류 (V1에서 생략)**  
> 결정일: 2026-06-08  
> 다음 검토: PDF 이미지 절차도 문서 비중 증가 시

---

## 1. 원래 목표 (구현계획서)

- PaddleOCR을 사용해 PDF 내부 **이미지 기반 절차도**에서 텍스트 추출
- 업무 절차 플로우차트를 검색 가능한 텍스트로 변환
- 성공 조건: 업무 절차 식별 가능

---

## 2. 보류 결정

V1 Baseline 구축 단계에서 **STEP 4를 진행하지 않기로 결정**함.

### 보류 이유

| # | 이유 | 상세 |
|---|------|------|
| 1 | 문서 형식 | 프로젝트 문서 **대부분이 HWPX**. OCR 대상 PDF 비중 낮음 |
| 2 | 사용자 결정 | *"일단 ocr은 제외하고 진행해줘"* — 명시적 제외 요청 |
| 3 | GPU 미사용 | PaddleOCR GPU(6GB) 활용 V1에서 보류, CPU OCR은 속도·품질 부담 |
| 4 | V1 범위 | V1 목표는 **Dense Vector RAG Baseline**. OCR은 핵심 경로 아님 |
| 5 | 대체 가능성 | HWPX `export_rich_markdown()`으로 표·본문 추출 이미 확보 (STEP 3) |

### 현재 파이프라인

```text
STEP 3 (파싱) → STEP 4 (생략) → STEP 5 (Chunking)
```

---

## 3. STEP 4가 필요해지는 시점

아래 조건 중 하나라도 해당되면 재검토:

- PDF 내 **이미지 절차도(플로우차트)** 문서가 RAG 품질에 필수일 때
- 스캔 PDF 등 **텍스트 추출 불가** 문서 비중이 커질 때
- PyMuPDF `get_text()`로 빈 결과가 나오는 PDF가 다수일 때
- 출장·휴가 등 절차도 기반 질의에서 검색 누락이 확인될 때

---

## 4. 재개 시 구현 예정 사항

| 항목 | 내용 |
|------|------|
| 라이브러리 | PaddleOCR |
| 대상 | PDF 내부 이미지 (절차도) |
| 입력 | `data/raw/` 내 PDF |
| 출력 | OCR 텍스트 → `data/processed/` 또는 파서 파이프라인 병합 |
| GPU | 6GB GPU 환경에서 선택적 활용 |
| 검증 | 절차도 OCR 결과 출력, 업무 절차 식별 가능 여부 |

## 5. V1에서의 영향

| 항목 | 영향 |
|------|------|
| HWPX 문서 | 없음 — STEP 3 파싱으로 충분 |
| 텍스트 PDF | 없음 — PyMuPDF (STEP 3)로 처리 |
| 이미지 절차도 PDF | **미처리** — 해당 내용 검색 불가 |
| Baseline 측정 | OCR 없는 상태로 Baseline 수치 확보 (비교 기준점) |
